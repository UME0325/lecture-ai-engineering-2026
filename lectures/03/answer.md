# 第3回 解答

## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  - 第1回の素のLLMは、講座を知らないまま「基礎・応用・発展」など一般論でもっともらしく答え、「どれか1つで完了」「採点しない」という肝心のルールに触れなかった
  - エージェントは用語集を引いてから答え、「基礎（講義内容の確認）・実装（自分でコードを書く）・発展（調査や試行）」「どれか1つで完了」「原則採点しない」を正しく示し、最後に「関連する回：第1回」と書いた
- `--trace` で見えたツール呼び出し（ツール名と引数）：
  - 「3レベル」の質問：`search_glossary({'query': '3レベル'})` を1回
  - 「LoRAとQLoRAの違いは？」：`search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` を、1回の応答の中で並べて呼んだ（2つの tool call の後に2つの tool return が続く）
- 1つの質問での LLM 呼び出し回数（`requests`）：
  - どちらの質問も `requests=2`（1回目でツールを呼ぶと決め、2回目で結果を読んで答える）。ツールを2つ呼んだ LoRA の質問でも、並列に呼んだので 2 のままだった
  - 入力トークンは 1,015（3レベル）と 1,428（LoRA）。ツールの結果が増えた分だけ入力が増えた
- 追加したツールが呼ばれたか：「第2回の確認問題を出して」で `make_quiz({'lecture': 2})` が呼ばれ（`requests=2`）、問題「『LoRA』の意味は？」だけを出して、答えは見せなかった。docstring の「答えは利用者が解答してから示すこと」が効いている
- 追加したツールと、docstring に書いた説明：
  - `make_quiz(lecture: int) -> str` を `app/tools.py` に追加し、`app/agent.py` で `agent.tool_plain(tools.make_quiz)` と登録した
  - docstring：「指定した回（1始まりの整数）の用語集から、確認問題を1問作って返す。『第2回の確認問題を出して』『第3回の内容で小テストして』のように、復習用の問題を求められたときに使う。返り値は問題（question）と答え（answer）の JSON。答えは利用者が解答してから示すこと。」
  - 使う場面を具体的な依頼文の形で書き、モデルが「いつ呼ぶか」を判断しやすくした。答えを先に見せないことも docstring に書いた（INSTRUCTIONS の「答えそのものは書かず、ヒントで導く」と方針をそろえるため）
  - 用語がない回（第0回・第5回など）では、問題を作れないことと、用語がある回の一覧を返す。`uv run pytest -q` は 21 件すべて成功した（講座 repo の第4回までの更新を取り込んだ状態）

## 宿題

- 取り組んだレベル：発展（b）Pi

### やったこと

1. Codespaces に Pi（`@earendil-works/pi-coding-agent` v1.5.0）を入れ、Gemini（`google/gemini-3.5-flash-lite`）で動かした
2. Pi のシステムプロンプトを、`system-prompt.ts` を読むだけでなく、パッケージの `buildSystemPrompt()` に既定のツール（read / bash / edit / write）の説明を渡して実際に組み立てた。結果は `lectures/03/pi/pi_default_prompt.txt`（約 2,100 字・34 行）。自分の `INSTRUCTIONS` は 218 字・6 行
3. 同じ質問を次の 3 つの構成に投げ、ツールの呼ばれ方と回答を比べた（`lectures/03/pi/run_compare.sh`）
   - 実験1：自作エージェント（専用ツール + `INSTRUCTIONS`）
   - 実験2：Pi（既定のシステムプロンプト + 汎用ツール）
   - 実験3：Pi に `--append-system-prompt` で自分の `INSTRUCTIONS` を足したもの（専用ツールは無いまま）
4. Pi の `--mode json` の出力から、`--trace` と同じ形でツール呼び出しを表示する `lectures/03/pi/pi_trace.py` を書いた

### 結果

#### システムプロンプトの比較：何が書かれていて、何が書かれていないか

| 観点 | Pi のシステムプロンプト | 自分の INSTRUCTIONS |
|---|---|---|
| 役割 | 「pi というハーネスの中で動くコーディング支援」 | 「AIE2026 の学習支援エージェント」 |
| ツールの一覧 | `<tools>` に1行ずつ書く（read: Read file contents など）。詳しい説明はツール定義の description 側 | 書かない。ツールの説明は docstring だけ |
| ツールの**使い方**（how） | 「cat ではなく read を使う」「edit の oldText は一意に一致させる」「write は新規か全面書き換えだけ」 | 書いていない |
| ツールを**使う場面**（when） | 書いていない。ツールを使えとも、確かめてから答えろとも書いていない | 「答える前に必ず search_glossary」「回の内容は get_lecture_summary」 |
| 根拠のないことへの態度 | 書いていない | 「用語集にないことは推測で断定せず、ないと伝える」 |
| 出力の形 | 「簡潔に」「ファイルパスをはっきり示す」 | 「最後に関係する回（第N回）を示す」 |
| 領域の方針 | なし | 「宿題の答えそのものは書かず、ヒントで導く」 |
| 安全（危険な操作の確認） | **なし**。確認を求めずに実行する | なし（読むだけのツールなので不要） |
| 環境の情報 | `<cwd>` に作業ディレクトリ | なし |
| 自分自身の説明書 | `<docs>` に置き場所だけ書き、「聞かれたときだけ読む」 | なし |
| 構造 | `<tools>` `<rules>` `<docs>` `<cwd>` などのタグで区切った部品を、実行時に組み立てる | 固定の文字列 |

Pi のプロンプトは、`buildSystemPromptSections()` が次の部品を組み合わせて作る。

- ツールごとの `promptSnippet`（`<tools>` の1行）と `promptGuidelines`（`<rules>` の箇条書き）。**そのツールが有効なときだけ**入る
- `AGENTS.md` / `CLAUDE.md`（`<project_context>`）、`APPEND_SYSTEM.md`、skills、拡張機能が足すセクション
- 部品ごとに差分を取り、変わった部品だけを会話の途中で差し替える（プロンプトキャッシュを無駄にしないため）

### 気づき・疑問

- **書く場所の分担が違う**。自作エージェントは「いつ使うか」を INSTRUCTIONS に、「何をするか」を docstring に書く。Pi は全体の指示を最小限にし、「どう使うか」を各ツールの定義に `promptGuidelines` として持たせている。ツールを外すとその指示も一緒に消えるので、指示とツールがずれない。演習で `make_quiz` を足したとき、INSTRUCTIONS に「確認問題には make_quiz を使う」と書くか迷ったが、Pi のやり方なら、その一文はツールの側に置くのが自然だと分かった
- **Pi は「確かめてから答えろ」と書いていない**。コーディングでは、ファイルを読まないと作業できないので、指示がなくても自然にツールを使う。一方、学習支援では、モデルは用語集を読まなくても「それらしく」答えられてしまうので、「必ず検索する」「推測で断定しない」と書く必要がある。システムプロンプトに書くべきことは、**モデルが放っておくとやってしまう失敗**で決まると考えた
- **安全はプロンプトではなく外側で守る**。Pi のプロンプトには「消す前に確認する」のような文が一つもない。公式の `docs/security.md` には「安全は、Pi がアクセスできるファイル・認証情報・ネットワークを制限することで得る。プロンプトやトランスクリプトの監視は境界にならない」とあり、講座が Codespaces で動かすよう指示している理由と一致する。宿題の実装レベルの `requires_approval=True` も、プロンプトで「確認してね」と頼むのではなく、コードで実行を止める仕組みで、考え方は同じ
- **同じ「エージェント」でも、何をハーネスに任せるかが違う**。Pi は `AGENTS.md` を自動で読むので、自分の INSTRUCTIONS を足すだけで、Pi が「grep で用語集を調べる学習支援エージェント」にもなる（実験3）。それなら専用ツールを作る意味は何か。実験の答えは**コストと確実さ**だった。「3レベル」の質問で、自作エージェントは 1,175 tokens・2回の呼び出しで済んだが、Pi はリポジトリを探し回って 34,453 tokens（約29倍）・7回かかった。INSTRUCTIONS を足しても 16,163 tokens で、用語集を丸ごと読むので、用語が増えるほど重くなる。専用ツールは「どこを・どう探すか」をコードに固定するので、モデルの探索を省き、毎回同じ手順で根拠を取れる
- **「確かめてから答えろ」が書いていないことの影響が、実験で見えた**。Pi は LoRA の質問でツールを使わず、一般知識で答えた。内容はおおむね正しいが、講座の用語集とは関係のない数値（VRAM の目安など）まで書き、どこに根拠があるかが分からない。学習支援で「必ず用語集を確認する」と書く意味は、正しさよりも「講座で教えた範囲と根拠に答えをそろえる」ことにあると分かった
- Pi のシステムプロンプトは英語だが、日本語の質問には日本語で答えた。一方、Pi の既定の「簡潔に」は守られず、LoRA の回答は比較表つきで 3,800 字を超えた。コーディング向けの「簡潔に」は、説明を求められた場面では効きにくいようだ
- 疑問： `promptGuidelines` 方式を Pydantic AI で真似るには、ツールの登録と一緒に INSTRUCTIONS を組み立てる関数（`@agent.instructions` で動的に作る）を書けばよいのではないか
